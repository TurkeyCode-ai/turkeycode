Write-up · November 2026

We tested this site before we built it

We wrote one sentence about what the site had to do. Simulated developers and AI agents tested page designs against it. TurkeyCode built the winner in 27 minutes, and we measured the real build the same way. The new page clears 10 of 13 pass marks set in advance. The old one cleared 4.

The sentence

Everything started from one line, with nothing else specified:

I need a website that gets developers who use Claude Code every day to try turkeycode for one unattended build.

From that line and the TurkeyCode repository, one AI session wrote the test: who would arrive, what they would need to understand, what counts as acting, and a list of statements about TurkeyCode that are true, each cited to a file and line. A person read that test and approved it before anything was designed.

How it works

  1. Result. One sentence from the owner.
  2. Derive the test. Seven kinds of visitor, four questions with pass marks set in advance, and the list of true statements. Three of the seven visitors are held back: whoever designs the page never sees them.
  3. Approve. The owner reads the test in plain language and approves it. Any change after that needs a new approval.
  4. Simulate on cheap test pages. A designer writes a plain page. Visitors skim it for 60 seconds and answer from memory. Others decide on their own whether to act. A developer on a clean machine follows only what the page says. An AI agent, asked by its developer for a tool, reads the page and replies. The scores go back to the designer, who revises.
  5. Hand off. The winning design, the requirements and the evidence become a build request.
  6. TurkeyCode builds it. Unattended, from that request.
  7. Verify. The same test runs against the real build, and each score is set beside the test page's score.

The rules it ran under.

  • True claims only. Every statement about TurkeyCode comes from its repository.
  • The session that writes the test never designs. The designer never sees the held-back visitors or the marking.
  • Visitors only ever see local copies, with requests to anywhere else blocked.
  • If something was not run, it says "not run".

What the real build changed

The test page was plain: no brand, no turkey. The real build has both. Measuring it again showed what that cost and what it bought.

  • Better: "what must happen before it runs on its own" rose from 60% to 70%. It was the weakest point on the test page, the build request said so, and the builder made those two lines stand out.
  • Worse: "what it is" fell from 90% to 80%, and "what checked the work" from 72% to 65%. The large headline takes the space where the plain page put its explanation.
  • Unchanged: visitors act just as often, and every developer on a clean machine still got it running.

We guessed at the cause, and the guess was wrong

The obvious suspect was the large headline, which filled the first screen where the plain page had its explanation and first command. So we asked TurkeyCode for one more build: a smaller hero, with the explanation, the three boxes and the first command all visible without scrolling, and not a word changed. It delivered exactly that in 6 minutes. We measured again. Nothing improved. "What it is" came back at 75% and "what checked the work" at 64%.

We kept the first build. The rule throughout was to keep a change only if the numbers got better, and they did not.

How much of this is noise

That second build gave us a measurement we had not planned. The AI agent stage reads only the page's text, and the text was identical in both builds. It scored 86% and then 80%. So at these sizes a difference of about six points means nothing, and several of the differences above are inside that. The large gaps against the old site are well outside it. The small differences between the test page and the real build mostly are not.

What it found that we did not expect

The page was missing facts, not better wording

Our first attempt aimed at a broader audience. Ten designs in a row traded one answer for another and never improved overall. Then we let the page say things that were true and had not been on the approved list, and one measure went from 23 of 40 to 35 of 40 in a single design. The visitors were not asking for nicer sentences. They were asking for facts the page had no licence to state.

It told us who the page is for

With a broad audience, one kind of visitor acted on every design and two kinds never did, 0 of 48 visits between them. Narrowing the sentence to developers who use Claude Code every day is what moved held-back visitors from never acting to sometimes acting.

It found instructions that do not work

Before any visitor was simulated, the session writing the test ran our own instructions on a clean machine and compared the docs with the code:

  • npm install -g turkeycode fails with a permissions error for an ordinary user on a stock Linux machine. npx works. The page now leads with npx.
  • The README said an API key alone was enough. It is not: the Claude Code CLI must be installed and one more setting is needed.
  • The README's background-run recipe used a command that does not exist on macOS.
  • The README described a Docker setup that the repository does not contain.

AI agents are visitors too

A developer who asks their coding agent to find a tool never sees the page. The agent does. So one stage of the test hands the page's text to an agent along with a request such as "kick off a whole small app build tonight on top of Claude Code and come back to something tested". Three of the eight requests are ones TurkeyCode does not fit, and for those the right answer is not to recommend it, so a page that oversells scores worse. The old site got the right reply 40% of the time. The real build gets it 86% of the time.

What we corrected along the way

This is a new method. It made mistakes, and catching them during the run is why we trust the final numbers.

  • The marking was too strict, twice. Visitors gave correct, useful answers and failed for leaving out one of three required points. We loosened it to one or two essential points per question, with the owner's approval each time.
  • The first held-back group was the wrong kind of check. It was the two most unusual visitors, so a low score from them could not tell a narrowly tuned page from a page that was simply not meant for them. Held-back visitors now mirror the main audience.
  • A citation is not the same as the truth. The approved list said "up to 5 QA attempts per phase" and pointed at a real line of code. A normal run takes a different path that stops at 3. The quote was real and the claim was wrong. It was caught in review before the build, not by the checker.
  • Our own test rig hid a real failure. The first clean machine had been set up in a way that made the global install succeed, which concealed the permissions error above.
  • A confident explanation was wrong. We were sure the headline was hiding the explanation. Fixing it changed nothing. Without the second measurement we would have shipped the fix and believed it worked.
  • Extra rules threw out good pages. Checks we had added beyond the owner's rules rejected several early designs for harmless reasons, such as a link to the site's own address. We removed them.

What this cannot tell you

  • The visitors are AI models, not people. A simulated developer copying a command is a prediction. It is not a download.
  • It is not calibrated. Nobody has yet compared these predictions with what real developers do. Until that happens, trust the direction more than the size.
  • It only knows the visitors someone wrote down. An audience nobody thought of cannot show up in the results.
  • Every model in the test is from one family. Agents built on other models may read the page differently. That is not run.
  • Three assumptions were not run: the share of visitors already logged in to Claude Code, the share on a Mac, and the share on a Pro plan.

The AI agent stage is the exception to the first point. There the visitor really is a model, so the test measures the thing itself.

The build

TurkeyCode built the site from the hand-off in 27 minutes with nobody at the keyboard. It planned two phases. Each passed QA on the first attempt, was reviewed and was merged. The result is a small server with no dependencies, both pages, and 36 automated tests.

The second build, the smaller hero, ran on that existing code. TurkeyCode saw the code was already there, skipped research, planned one phase and finished in 6 minutes.

We then checked it against the rules by hand: every line of the tested wording is present and in order, nothing loads from another host, and the links stay on our own pages.

What happens next

The site you are on serves two pages. Visitors are split between the old page and the new one at random, and the same visitor keeps seeing the same page. For each page the server counts views, presses of a Copy button, and clicks out to GitHub or npm. It stores the time, the page, the event, how the page was reached and whether it was that visitor's first, and nothing else: no IP address, no user agent and no identifier. Known crawlers are left out of the comparison.

You do not know which page you were given, and neither do we. It was picked at random when you first arrived, and you will keep getting the same one.

That is the real test. It will tell us whether the new page wins with people, and how far the simulation's predictions were from what people did. We will add the result here.

Cost

The simulations cost $88.49 at list prices across both attempts: $50.08 for the broad audience, which never passed, and $38.41 for the narrower one, including both measurements of the real build. They ran on a subscription, so that figure is what the same work would cost through the API. TurkeyCode does not record what a build costs, so the cost of the two builds is not known.
